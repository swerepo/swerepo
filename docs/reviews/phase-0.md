### Reviewer: findings

#### P0-F01 · blocker · `.github/workflows/ci.yml:96`
**Problem:** `uv run seamspec doctor --ci` fails unconditionally on a root commit when `ci.yml` runs on `push` to `main`, and on multi-commit pushes to `main` it only checks `HEAD~1` rather than the pushed commit range. In SeamSpec 0.1.1 (`seamspec/core/doctor.py`), `default_base()` uses `origin/$GITHUB_BASE_REF` when `GITHUB_BASE_REF` is set (`pull_request` only) and falls back to `HEAD~1` otherwise; if `HEAD~1` cannot be resolved, `_forward_only()` records `error · forward-only · can't read HEAD~1` and `doctor --ci` exits `1`.
**Scenario:** Phase 0 is committed as the initial commit on `main` and pushed to GitHub (`gh repo create --source . --push`, spec §12) → `ci.yml` triggers on `push` → `GITHUB_BASE_REF` is empty and `HEAD~1` does not exist → `seamspec` job exits `1` → `ci-ok` fails on the repository's first CI run. (On a later 2-commit push to `main`, `HEAD~1` also misses ledger mutations in the earlier commit of the push.)
**Recommendation:** Keep `uv run seamspec doctor --ci` on `pull_request`; on `push`, pass `--base "$BEFORE"` when `github.event.before` is non-zero and reachable, falling back to `--base HEAD` when `HEAD~1` does not exist (initial commit, so config, schema, provenance, integrity, and fingerprint checks still run cleanly). Keep this same edge case in mind in Phase 7 when generating `golden-ci.yml` for newly initialized single-commit repositories.

#### P0-F02 · blocker · `.seamspec/proposed/inv_62d51113/test_inv_62d51113.py:48`
**Problem:** Two issues must be resolved before `inv_62d51113` is hash-locked:
1. `CODE_REVIEW.md:66` contains an unescaped non-placeholder home path example (`/Users/` + a real-looking name, added in Design Note 4 after the manual 33-file scan), which already triggers `_findings()`, and `CODE_REVIEW.md` is persisted to `docs/reviews/phase-0.md` on close (ADR-20261119-9f87).

Once approved, the test is hash-locked and cannot add these without a supersede.
**Scenario:** (1) The owner approves `inv_62d51113` and runs `git add . && git commit` to land Phase 0 → `seamspec verify --all --gate` fails on `CODE_REVIEW.md:66` (`home-folder path`) and blocks the commit. #### P0-F03 · should-fix · `.seamspec/proposed/inv_62d51113/test_inv_62d51113.py:18`
**Problem:** Three detection/traversal edge cases in `test_inv_62d51113.py` that will be frozen once hashed:
1. `HOME` (`line 18`) matches only single backslashes (`[A-Za-z]:\\Users\\`), missing Windows home paths escaped inside JSON, TOML double-quoted strings, or Python string literals (`"C:\\Users\\<person>\\..."`). Conversely, its capture group `([A-Za-z0-9._-]+)` starts with `.`, so prose ellipses like `/Users/` followed by three ASCII dots match `...` and get flagged as a real user.
2. `_allowed_email` (`line 45`) checks `domain.endswith(ALLOWED_EMAIL_DOMAINS)` without a dot boundary (matching e.g. `evilnoreply.github.com`), and `local == "git"` allows any `git@<domain>` email in prose rather than only git SSH remotes.
3. `_tracked_files` (`line 30`), used when `(ROOT / ".git").exists()` is false (SeamSpec's staged commit snapshot, `git archive` exports, or container builds), runs `ROOT.rglob("*")` without excluding `.seamspec/.local`, `.venv`, `venv`, `node_modules`, `__pycache__`, `.pytest_cache`, or `.ruff_cache`.
**Scenario:** (1) A `.json` or `.py` file containing `"C:\\Users\\<realname>\\project"` is committed → `HOME.findall(...)` returns `[]` and the Windows home path leaks into git history; meanwhile a doc line writing `/Users/` + `...` fails the check. (2) Running `seamspec verify --all` in an unpacked archive/container without `.git` after `uv sync` walks `.venv/` (a real directory there, unlike `snapshot.py`'s symlink) and fails on third-party package `METADATA` author emails; or on Windows `verify --gate`, JUnit XML written under `.seamspec/.local/reports/` records the temp snapshot path under the user's Windows home directory and fails the gate.
**Recommendation:** Change `HOME` to `r"(?:/Users/|/home/|[A-Za-z]:\\+Users\\+)([A-Za-z0-9_][A-Za-z0-9._-]*)"`; check `domain in ALLOWED_EMAIL_DOMAINS or domain.endswith(tuple("." + d for d in ALLOWED_EMAIL_DOMAINS))`; use `EMAIL.finditer(line)` and restrict `git@` to SSH remotes (`:` immediately after the domain or `ssh://` immediately before `git@`); and skip `.seamspec/.local`, `.venv`, `venv`, `node_modules`, `__pycache__`, `.pytest_cache`, and `.ruff_cache` in the non-`.git` `rglob` fallback.

#### P0-F04 · should-fix · `docs/progress/20261119-phase-0-skeleton.md:3`
**Problem:** `.git/HEAD` currently points to `refs/heads/main` (unborn), whereas `docs/progress/20261119-phase-0-skeleton.md:3` and `:16` record `**Branch:** phase-0/skeleton` and `Commit on phase-0/skeleton with the owner's go-ahead`, and `AGENTS.md:8` / `CONTRIBUTING.md:7` forbid committing directly to `main` without noting the initial-commit bootstrap case from spec §12 (`line 449`: "commit the files to the default branch (the only commit that goes straight to it, since no rules exist yet)").

**Recommendation:** Decide and align before committing: either treat Phase 0 as the initial bootstrap commit on `main` (per spec §12, updating `docs/progress/20261119-phase-0-skeleton.md` and noting the bootstrap exception in `ADR-20261119-75e6`), or document how `main` is rooted before `phase-0/skeleton` branches off.

#### P0-F05 · should-fix · `docs/adr/ADR-20261119-6b94-seamspec-governs-this-repo.md:23`
**Problem:** `ADR-20261119-6b94` pins `seamspec==0.1.1` in `[dependency-groups] dev` ("so the lockfile decides the version for every machine and CI", rejecting global install) and `README.md:14` / `AGENTS.md:19` list only `uv sync`. However, `.git/hooks/pre-commit` (installed by `seamspec init`) and the Claude Code `seamspec@seamspec` plugin (`.claude/settings.json`) execute `seamspec` from `PATH` / `$HOME/.local/bin`, not `.venv/bin/seamspec`.

### Reviewer: answers to questions

1. **Spec gap (`seamspec` CI vs `ci-ok`):** **Option (a) is strongly better** whenever the `ci` component is active, for an additional reason beyond keeping a single `ci-ok` check: SeamSpec 0.1.1's own generated `.github/workflows/seamspec.yml` uses mutable action tags (`actions/checkout@v4`, `astral-sh/setup-uv@v6`) without `persist-credentials: false` or `timeout-minutes`, so Golden Repo's `zizmor` `workflow-audit` job would flag `seamspec.yml` out of the box. Running `seamspec init --mode enforced --no-ci` and putting the `seamspec` job (including `doctor --ci`, `verify --all --ci`, and `spec --check`, with the root-commit fix from `P0-F01`) inside `golden-ci.yml` keeps one required check and SHA-pinned hardening. Two edge cases to record in the ADR + spec update when you settle this (before Phase 4/7): (i) if a user runs `goldenrepo init --only seamspec` *without* the `ci` component, fall back to `seamspec init --ci` or warn that no workflow runs SeamSpec; (ii) `--no-ci` works cleanly because Golden Repo uses `--mode enforced` (SeamSpec's `strict` mode expects `seamspec.yml`).
2. **Privacy allowlist:** The placeholder user set (`me, user, you, username, name, runner`) is sound (you may optionally add `runneradmin` for GitHub's Windows runner and `Shared` for macOS shared folders). However, `local == "git"` and `domain.endswith(...)` are slightly too permissive, single-backslash Windows `HOME` misses JSON/TOML/Python-escaped `"C:\\Users\\<person>\\..."` paths (while flagging ASCII `...` ellipses), and omitting §6.4's `goldenrepo: allow-privacy` / `[privacy] allow_paths` / `SECURITY.md` / `pyproject.toml` allowances will cause guaranteed false alarms (`CODE_REVIEW.md:66` already trips it). See `P0-F02` and `P0-F03`.
3. **Typer vs argparse:** **Keep Typer** (ADR-20261119-db50 holds up). Its transitive footprint in `uv.lock` is 7 pure-Python wheels (`typer`, `click`, `rich`, `markdown-it-py`, `mdurl`, `pygments`, `shellingham`) with no native extensions, and in target repositories' CI Golden Repo runs in an isolated `uvx` tool environment rather than the target project's own dependencies. Sharing patterns and `CliRunner` idioms with SeamSpec across ~9 subcommands outweighs saving a few pure-Python wheels—just ensure `--json` outputs bypass Rich line-wrapping in Phase 2+.
4. **Approve the two rules as they are?** **Not yet for `inv_62d51113`; fix `P0-F02` and `P0-F03` first, then lock.** Locking `inv_62d51113` as-is would immediately block committing `CODE_REVIEW.md:66` and force a supersede in Phase 2 / when `SECURITY.md` is added. `inv_b2000e40` works now, though applying the small regex polish in `P0-F07` while still unlocked is cheap.

#### P0-F02 · **Fix** (1 and most of 2) · **Push back** (`.golden.toml` `allow_paths`)

#### P0-F03 · **Fix** (all three)
